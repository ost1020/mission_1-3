# Mini NPU Simulator

## 1. 실행 방법
* **실행 환경:** Python 3.8 이상 (외부 라이브러리 미사용, 표준 라이브러리 `time`, `json`, `os`만 사용)
* **실행 명령어:** `python3 main.py`
* **데이터 위치:** `main.py`와 동일한 디렉토리에 `data.json` 파일 배치
* **모드 선택:** 실행 후 콘솔 안내에 따라 모드 번호 입력
  * `1`: 사용자 입력 (3×3 필터 A/B 및 패턴 직접 입력 또는 패턴 생성기 재활용)
  * `2`: `data.json` 일괄 분석 및 크기별 성능 벤치마크
  * `3`: 보너스 모드 (크기 N 패턴 자동 생성 및 2D vs 1D 성능 비교)

### 실행 예시 (모드 1 샘플)
```text
=== Mini NPU Simulator ===
[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택: 1
필터 A (3줄 입력, 공백 구분)
0 1 0
1 1 1
0 1 0
필터 B (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1
패턴 (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1

#---------------------------------------
# [3] MAC 결과
#---------------------------------------
A 점수: 1.0
B 점수: 5.0
연산 시간(평균/10회): 0.001 ms
판정: B
```

## 2. 구현 요약
* **라벨 정규화 (`DataValidator.normalize_label()`):**
  * `data.json` 내부에서 파편화된 표기(`+`, `cross`, `x`)를 공백 제거 및 소문자 변환 후 시스템 표준 라벨(`Cross`, `X`)로 통일함.
  * **신규 라벨 확장 체크리스트:** `normalize_label()` 분기 추가 → `data.json` 필터·패턴 테스트 케이스 추가 → 미지원 라벨 입력 시 의도된 `FAIL` 처리 및 리포트 출력 검증.
* **MAC 연산 구현 (`MACProcessor.calculate_mac()`):**
  * NumPy 등 외부 라이브러리 없이 이중 `for`문으로 입력 패턴과 필터를 위치별로 곱하고 누적 합산(`+=`)함.
  * **유사도 판정 원리:** 입력 패턴과 필터의 형태가 겹치는 위치(1과 1이 일치하는 좌표)에서만 양의 값이 누적되므로, MAC 총점이 클수록 해당 필터와 기하학적으로 더 유사함을 의미함.
* **동점 처리 정책 (`MACProcessor.judge_score()`):**
  * IEEE 754 부동소수점 누적 반올림 오차로 인한 오판정을 막기 위해 `abs(score_a - score_b) < 1e-9` (epsilon) 조건 충족 시 `UNDECIDED`로 판정함.
  * **모드별 정책 분리 의도:** 모드 1(대화형 테스트)에서는 사용자가 미세 오차로 인한 동점 상황을 직접 인지하도록 `판정 불가 (|A-B| < 1e-9)`를 안내하고, 모드 2(자동화 배치 검증)에서는 단일 정답(`expected`)과 일치하지 않는 모호한 판정을 허용하지 않기 위해 `UNDECIDED`를 엄격하게 `FAIL`로 집계함.
  * **Epsilon 선택 근거 및 민감도:** 64비트 float의 머신 엡실론(~`2.22e-16`)과 `25×25`(625회) 누적 오차 수준(`1e-15`~`1e-14`)을 안전하게 흡수하면서 유의미한 점수 차이는 보존하기 위해 `1e-9`를 채택함. `N`이 수천 단위로 커지거나 단정밀도(float32) 환경일 경우 `1e-6` 수준으로 완화가 필요하며, 반대로 `1e-16` 이하로 과도하게 축소하면 부동소수점 오차를 걸러내지 못해 오판정이 발생함.

## 3. 결과 리포트

### 3.1 `data.json` 실제 실행 결과 요약
* **전체 통계:** 총 테스트 **6개** / 통과(**PASS**) **3개** / 실패(**FAIL**) **3개**
* **통과 케이스 (3건):**
  * `size_5_2`: Cross `8.9` vs X `0.1` → 판정 `Cross` | expected `Cross` | **PASS**
  * `size_13_1`: Cross `0.3` vs X `14.700000000000008` → 판정 `X` | expected `X` | **PASS**
  * `size_25_2`: Cross `52.9` vs X `0.1` → 판정 `Cross` | expected `Cross` | **PASS**
* **실패 케이스 (3건):**
  * `size_5_1`: Cross `0.9` vs X `0.8999999999999999` (차이 약 `1.1e-16`) → 판정 `UNDECIDED` | expected `X` | **FAIL**
  * `size_13_2`: Cross `7.499999999999997` vs X `7.5` (차이 약 `2.7e-15`) → 판정 `UNDECIDED` | expected `Cross` | **FAIL**
  * `size_25_1`: Cross `4.9` vs X `4.899999999999999` (차이 약 `8.9e-16`) → 판정 `UNDECIDED` | expected `X` | **FAIL**

### 3.2 실패 원인 분리 진단 (데이터/스키마 vs 로직 vs 수치 비교)
1. **데이터/스키마 문제 (해당 없음):** `size_5`, `size_13`, `size_25` 필터가 모두 정상 로드되었으며, 모든 패턴의 키 파싱 및 행·열 차원 검증에서 크기 불일치 오류는 발생하지 않음.
2. **로직 문제 (해당 없음):** `+`, `cross`, `x` 라벨 정규화와 필터 매칭이 정상 작동하여 점수 차이가 명확한 3건(`size_5_2`, `size_13_1`, `size_25_2`)은 100% 정확히 통과함.
3. **수치 비교 및 동점 정책 문제 (FAIL 3건의 직접 원인):**
   * 실패한 3개 케이스(`size_5_1`, `size_13_2`, `size_25_1`)는 수학적으로 Cross와 X 필터 점수가 각각 `0.9`, `7.5`, `4.9`로 완전히 동일한 동점 입력임.
   * 파이썬 64비트 부동소수점(IEEE 754)의 이진 변환 및 누적 덧셈 과정에서 `1e-16` ~ `1e-15` 수준의 미세 반올림 오차가 발생함(`size_13_1`의 `14.700000000000008`에서도 동일한 누적 오차 현상이 관측됨).
   * 만약 `epsilon` 정책 없이 단순 대소 비교(`>`)를 적용했다면, 세 케이스 모두 미세 오차 때문에 오히려 **정답과 반대되는 라벨**(`size_5_1`→Cross, `size_13_2`→X, `size_25_1`→Cross)로 오판정되는 심각한 논리 오류가 발생했을 것임.
   * 허용오차(`1e-9`) 기반 동점 처리 정책이 정상 작동하여 거짓 승자를 차단하고 `UNDECIDED`로 방어적 분류를 수행했으며, 모드 2의 엄격한 비교 규칙(`UNDECIDED != expected`)에 따라 의도된 `FAIL`로 집계됨.

### 3.3 시간 복잡도 분석 (O(N²)) 및 실측 표 해석
I/O(파일 로드·콘솔 출력)를 배제하고, 캐시 워밍업 1회 후 고해상도 단조 타이머(`time.perf_counter()`)로 순수 MAC 연산 구간만 **10회 반복 측정**한 실제 결과는 아래와 같음.

| 패턴 크기 (N×N) | 평균 연산 시간 (ms, 10회 평균) | MAC 연산 횟수 (N²) | 이전 크기 대비 연산량 배율 | 이전 크기 대비 시간 배율 |
| :---: | :---: | :---: | :---: | :---: |
| **3×3** | 0.001 | 9 | - | - |
| **5×5** | 0.002 | 25 | 2.78배 | 2.00배 |
| **13×13** | 0.008 | 169 | 6.76배 | 4.00배 |
| **25×25** | 0.028 | 625 | 3.70배 | 3.50배 |

* **O(N²) 복잡도 실측 근거:** MAC 연산은 N×N 2차원 리스트를 이중 반복문으로 순회하므로 총 곱셈·누적 및 메모리 접근 횟수가 정확히 `N²`에 비례함.
* **크기별 스케일링 해석:** `3×3`~`5×5` 같은 초소형 구간에서는 함수 호출 및 파이썬 인터프리터 루프 초기화 같은 고정 오버헤드 비중이 커서 시간 증가율이 연산량 증가율보다 완만하게 나타남. 그러나 크기가 커진 `13×13` → `25×25` 구간에서는 연산 횟수가 **3.70배(169→625)** 증가할 때 평균 실행 시간도 **3.50배(0.008ms→0.028ms)** 증가하여, 데이터 규모가 커질수록 실행 시간이 `O(N²)` 법칙에 강하게 수렴함을 실측으로 확인함.

### 3.4 CPU vs NPU 병목 비교 및 최적화 전략
* **CPU의 직렬 처리 병목:** 본 시뮬레이터가 구동되는 CPU는 복잡한 제어 로직과 순차 명령 실행에 특화되어 있어 `N²`번의 MAC 연산을 직렬(순차)로 처리함. 특히 파이썬 2차원 리스트(`pattern[i][j]`)는 행 포인터 → 열 원소로 이어지는 2단계 포인터 역참조(Memory Fetch)가 매 연산마다 발생해, 대형 필터(수백×수백 이상) 환경에서 메모리 접근과 순차 루프가 핵심 병목 지점이 됨.
* **NPU의 병렬 처리 구조:** 반면 AI 전용 칩인 NPU는 수천 개의 MAC 연산기(ALU/Systolic Array)를 물리적으로 배치해 입력 패턴과 필터 가중치를 동시에 쏟아부어 병렬 연산함. 데이터 재사용률을 극대화해 메모리 대역폭 병목을 줄이고, 단일 클럭 사이클당 수많은 MAC을 동시 처리함으로써 실효 연산 지연을 획기적으로 단축함.
* **소프트웨어 최적화 우선순위:** CPU 환경에서 MAC 연산 병목을 완화하기 위한 최적화는 **1차원 배열 평탄화(Flattening, 포인터 역참조 뎁스 축소 및 캐시 지역성 개선) → 캐시 블로킹(Loop Blocking) → SIMD 벡터화 및 저수준 C/네이티브 확장** 순으로 우선 적용하는 것이 효과적임.
